# 背景
1.背景：
“水木汇”作为清华校园的活动报名小程序，在院系组织发起的抢票类活动（限额报名、先到先得）下，前端会在短时间内触达大量并发用户。当前后端为 Node.js + MongoDB，前端为微信小程序，单台数据库的原子写成为瓶颈（约 20 条/秒），前端频繁拉取活动介绍图片又给服务器和网络造成压力。为了保证用户体验与平台稳定性，需在不完全更换硬件的前提下，通过架构优化将系统改造为“前端快速响应 + 后端异步持久化”的模式。

2.需求：
为微信小程序“水木汇”提供一套可执行的高并发改造方案，目标在现有学校租用虚拟机（Westmere 16核/32GB/TopHC vHDD）条件下，将并发能力从当前瓶颈（DB原子写 20 tps）提升到 **5k–10k 并发请求处理能力**（注意：并发连接与后端可持续TPS是两个度量，本文中目标为能在抢票场景下短时间内并发接收并快速返回结果，最终数据库写入将异步化，能够稳定承受峰值压力）。

## 后端重构
后端重构为go
- 如果你的系统**瓶颈确实在 Node.js 的并发与 GC 开销**，迁移到 Go **理论上可以提升 5–10 倍性能**；
- 但如果瓶颈是数据库写入或架构设计（例如同步写 MongoDB），**换语言几乎无效**；
- 对于“抢票场景”，**Go 更合适**，因为它能承受突发高并发并快速返回响应。

# 架构考虑点
- **负载均衡 / 反向代理**（nginx / traefik）：SSL、连接复用、静态缓存、速率限制入口。
- **应用层（Node.js）**：若干无状态实例，负责接收请求、做快速原子判断（参见 Redis Lua），将“成功预占/抢票结果 + 事件”入队，然后立即响应前端（成功/失败）。短请求时延。
- **Redis（主内存缓存 + 队列/流）**：
    - 用作抢票的**计数器/库存管理**（原子递减由 Lua 脚本完成）。
    - 用作**轻量队列/Stream** 保存事件，用于后端异步持久化。
    - 也可用于幂等/限流（token bucket）、黑名单与防刷。
- **后台工作进程（Worker，Node.js 或 Go）**：
    - 从 Redis Stream（或 List）消费事件，做**批量写入 MongoDB**（bulkWrite，ordered: false）。
    - 失败重试、死信队列、告警。
- **MongoDB（现有）**：
    - 保持为最终持久化存储，写入策略调整为异步批量写、较低写一致性（w:1 可选）以换吞吐。
- **静态资源/图片**：
    - 抽取并迁移到 CDN 或对象存储（如腾讯 COS / 阿里 OSS / 七牛），并设置 aggressive 缓存（Cache-Control）。
    - 小程序端使用本地缓存、适当压缩图片、懒加载。
- **监控与告警**：Prometheus + Grafana 或直接云监控，采集 Redis 队列长度、请求延迟、后端批量写吞吐、错误率、qps。
- **限流 & 防刷**：请求入口（nginx + Redis）做漏桶/令牌桶限流 + 验证码/行为风控策略。
# 基本技术
## k3s
**K3s 是一个经过优化和精简的 Kubernetes 发行版**
特点：
- **轻量级**​： 所有组件都打包成一个小于 100MB 的二进制文件，启动速度快，内存占用极低。
- ​**简化安装**​： 只需一条命令即可完成一个节点的安装和配置，大大降低了入门和运维复杂度。
- ​**低资源消耗**​： 非常适合在边缘计算、物联网设备、开发机、ARM 架构设备（如树莓派）上运行。
- ​**兼容性**​： 100% 兼容原生 Kubernetes 的 API。这意味着为原生 Kubernetes 编写的 YAML 配置文件和应用，通常可以无缝地在 K3s 上运行。
- ​**内置组件**​： 它用轻量级的替代品替换了 Kubernetes 的一些资源密集型组件（如用 SQLite 替代 etcd 作为默认存储），并内置了常用的组件（如 Helm controller, Traefik Ingress controller），开箱即用。

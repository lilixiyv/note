# 背景
1.背景：
“水木汇”作为清华校园的活动报名小程序，在院系组织发起的抢票类活动（限额报名、先到先得）下，前端会在短时间内触达大量并发用户。当前后端为 Node.js + MongoDB，前端为微信小程序，单台数据库的原子写成为瓶颈（约 20 条/秒），前端频繁拉取活动介绍图片又给服务器和网络造成压力。为了保证用户体验与平台稳定性，需在不完全更换硬件的前提下，通过架构优化将系统改造为“前端快速响应 + 后端异步持久化”的模式。

2.需求：
为微信小程序“水木汇”提供一套可执行的高并发改造方案，目标在现有学校租用虚拟机（Westmere 16核/32GB/TopHC vHDD）条件下，将并发能力从当前瓶颈（DB原子写 20 tps）提升到 **5k–10k 并发请求处理能力**（注意：并发连接与后端可持续TPS是两个度量，本文中目标为能在抢票场景下短时间内并发接收并快速返回结果，最终数据库写入将异步化，能够稳定承受峰值压力）。

# 改进点

## Redis

进行抢票服务的原子抢占，后续再异步入库（mongodb）

## 后端重构

后端重构为go
- 如果你的系统**瓶颈确实在 Node.js 的并发与 GC 开销**，迁移到 Go **理论上可以提升 5–10 倍性能**；
- 但如果瓶颈是数据库写入或架构设计（例如同步写 MongoDB），**换语言几乎无效**；
- 对于“抢票场景”，**Go 更合适**，因为它能承受突发高并发并快速返回响应。
- 中长期方案
## 反向代理
使用nginx进行反向代理
- 对静态文件进行分流
- 开启静态文件压缩与缓存

- 不必要，若静态图片数量庞大或有鉴权需求，则考虑

# 架构考虑点
- **负载均衡 / 反向代理**（nginx / traefik）：SSL、连接复用、静态缓存、速率限制入口。
- **应用层（Node.js）**：若干无状态实例，负责接收请求、做快速原子判断（参见 Redis Lua），将“成功预占/抢票结果 + 事件”入队，然后立即响应前端（成功/失败）。短请求时延。
- **Redis（主内存缓存 + 队列/流）**：
    - 用作抢票的**计数器/库存管理**（原子递减由 Lua 脚本完成）。
    - 用作**轻量队列/Stream** 保存事件，用于后端异步持久化。
    - 也可用于幂等/限流（token bucket）、黑名单与防刷。
- **后台工作进程（Worker，Node.js 或 Go）**：
    - 从 Redis Stream（或 List）消费事件，做**批量写入 MongoDB**（bulkWrite，ordered: false）。
    - 失败重试、死信队列、告警。
- **MongoDB（现有）**：
    - 保持为最终持久化存储，写入策略调整为异步批量写、较低写一致性（w:1 可选）以换吞吐。
- **静态资源/图片**：
    - 抽取并迁移到 CDN 或对象存储（如腾讯 COS / 阿里 OSS / 七牛），并设置 aggressive 缓存（Cache-Control）。
    - 小程序端使用本地缓存、适当压缩图片、懒加载。
- **监控与告警**：Prometheus + Grafana 或直接云监控，采集 Redis 队列长度、请求延迟、后端批量写吞吐、错误率、qps。
- **限流 & 防刷**：请求入口（nginx + Redis）做漏桶/令牌桶限流 + 验证码/行为风控策略。

# 基本技术

## k3s
**K3s 是一个经过优化和精简的 Kubernetes 发行版**
特点：
- **轻量级**​： 所有组件都打包成一个小于 100MB 的二进制文件，启动速度快，内存占用极低。
- **简化安装**​： 只需一条命令即可完成一个节点的安装和配置，大大降低了入门和运维复杂度。
- **低资源消耗**​： 非常适合在边缘计算、物联网设备、开发机、ARM 架构设备（如树莓派）上运行。
- **兼容性**​： 100% 兼容原生 Kubernetes 的 API。这意味着为原生 Kubernetes 编写的 YAML 配置文件和应用，通常可以无缝地在 K3s 上运行。
- **内置组件**​： 它用轻量级的替代品替换了 Kubernetes 的一些资源密集型组件（如用 SQLite 替代 etcd 作为默认存储），并内置了常用的组件（如 Helm controller, Traefik Ingress controller），开箱即用。
## OSS
对象存储服务，分为云存储方案如腾讯云等和本地方案如minIO

# 日程安排
#### 需求分析（约 3 天）

首先需要对现有系统进行详细的分析，确认瓶颈所在。团队将审查现有的前端与后端代码，特别是数据库原子写操作的瓶颈，并分析当前系统在处理高并发请求时的性能表现。这一过程的重点是确认系统中的性能瓶颈，特别是在 MongoDB 写操作上。

#### 系统设计（约2天）

随后，基于对现有瓶颈的分析，团队将设计新的架构方案。方案中将引入 Redis 来处理高并发请求，通过 Redis 缓存实现库存预占和抢票功能，并通过 Redis 异步队列将请求推送到后台进行处理。此外，Nginx 将用于静态资源的缓存与反向代理，以减轻服务器的负担。系统架构设计完成后，明确项目需求和每个模块的开发任务，为后续的开发提供清晰的方向。

#### redis与mongo模块（约 5 天）

后端将实现 Redis 的库存管理与抢票逻辑，使用 Redis Lua 脚本实现库存扣减和预占功能，确保在高并发的场景下能够完成原子操作。同时，Redis 将作为一个异步队列，处理抢票成功的请求并推送到后台系统进行异步写入。

MongoDB 的数据库写入优化也是本阶段的核心任务。通过实现 MongoDB 的批量写入功能，减少频繁数据库访问带来的性能瓶颈，确保数据库能够处理更高并发的写入请求。

#### nginx模块（约3天）

Nginx 的配置优化将重点关注静态资源缓存和压缩策略，以减轻前端请求的压力。通过合理配置，Nginx 将有效提高静态资源的响应速度，并减少服务器的负担。

#### 前端对接（约3天）

调整小程序侧接口，确保前端能及时接收到抢票结果，同时确保后台能够高效地处理并发请求。完成接口开发后，将进行单元测试，验证各模块的基本功能是否正常工作。

#### 性能优化与压力测试（约 5天）

首先对Redis 进行性能调优，调整连接池和缓存策略，确保其能够在高并发下稳定运行。对于 MongoDB，我们将优化批量写入操作，调整大小与频率，确保其在高并发场景下能够高效执行。

Nginx 的优化将聚焦于高效的静态资源缓存与压缩设置，进一步提升响应速度并降低网络带宽消耗。此外，Nginx 还将负责反向代理流量，分配负载，确保服务器能够稳定应对大量并发请求。

接下来，团队将进行压力测试，使用压测工具（如 wrk、Locust）模拟 5k–10k 并发请求，测试 Redis、MongoDB 和 Nginx 在高并发下的性能。通过测试，可以找出性能瓶颈，并进行针对性优化。

在性能优化过程中，前后端的联调也将进行，确保用户在高并发场景下能够获得快速响应，同时数据能够正确写入数据库。

#### 系统集成与部署（约 2 天）

进行全面的集成测试，确保每个模块与系统的各个部分能够高效协作，验证系统的整体表现。

集成测试将包括前后端接口的功能验证、Redis 与 MongoDB 的数据一致性测试、Nginx 的负载均衡效果等。通过一轮完整的测试，团队将检查系统是否能够在实际环境下处理高并发请求，并确保没有任何重大问题。

系统部署将采用分阶段进行。首先在测试环境中进行部署，验证所有服务的配置与运行情况。接着，将在生产环境中进行最终部署，配置负载均衡、高可用性和监控系统，确保系统在上线后能够稳定运行。
# 整体设计
初步方案为加入redis进行抢票业务处理，由rabbitmq（消息队列）进行持久化数据的异步写入，静态图片资源由nginx处理。
初步设计的架构如下：
![[server_base_arch.excalidraw]]
- nginx:
	- 代理服务器，客户端直接访问的接口
	- 根据客户端的请求：
		- 若为静态图片资源请求：直接返回
		- 需后端处理：转发给node.js
- node.js
	- 后端服务器，负责业务逻辑
	- 对于对数据的查询等操作，先对redis进行查询，未命中则查询mongodb并更新redis
	- 对数据的更新操作，借助消息队列rabbitmq异步更新mongodb
- redis
	- 缓存服务，提供对数据的快速访问
- mongodb
	- 数据库，负责数据的持久化存储
- rabbitmq
	- 消息队列，负责调度大量数据的写入
